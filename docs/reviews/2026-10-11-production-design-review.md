## Findings

All findings below reproduce against the immutable branch candidate `dc5559b0d077ca3dcca78257889c4c8e59d3d3f9`, not the protected uncommitted duration/dependency experiments. No P0 was established. Five P1 and five P2 findings were established, including the focused same-day MinIO policy addendum D10; explicit limitations are separated later.

### D1 [P1] Default Join Does Not Implement CI-Owned Shared Launch Completion

- Sources: [formatter.rb:729](</Users/nick/Documents/New project/lib/reportportal_cucumber/cucumber/formatter.rb:729>), [join.rb:72](</Users/nick/Documents/New project/lib/reportportal_cucumber/runtime/join.rb:72>), [config.rb:30](</Users/nick/Documents/New project/lib/reportportal_cucumber/config.rb:30>).
- Scenario and impact: the first isolated Cucumber process becomes primary and finishes the shared launch as soon as its own run ends, even if another worker is still executing. A later worker ignores the original sync state once the primary PID exits and creates a second launch while the secondary is still alive. This breaks completeness and ownership for the requested production topology. Launch-name/project/endpoint matching also provides no explicit CI run identity. There is no public configuration for an externally supplied launch UUID plus worker-side suppression of launch finish; setting `join=false` creates separate launches, not CI-owned sharing.
- Evidence: `probes.rb` observed `primary_finished_launch=true` with one secondary scenario still open, and `secondary_finished_launch=false`. The actual fork/filesystem probe `join_fork.rb` observed the secondary alive on the original UUID while the late participant created a different launch and became primary. These are independent local lifecycle/coordination probes, not a claim about how the deployed RP server responds to early finish. The existing fork spec verifies initial UUID sharing only while the primary stays alive.
- Mitigation/gate: provide and test the explicit CI-owned launch contract, unique run-scoped coordination, and completion after every worker's reporting outcome is collected. Until then, permit only independent per-worker launches for a restricted pilot. Do not recommend default `join=true` as safe production shared completion. The implementation contract explicitly assigns shared completion to CI, but the shipped formatter assigns it to a worker.

### D2 [P1] HTTP Evidence Leaks Credentials Under Escaped Keys In Embedded Or Malformed JSON

- Sources: [evidence_redactor.rb:87](</Users/nick/Documents/New project/lib/reportportal_cucumber/automation/evidence_redactor.rb:87>), [evidence_redactor.rb:117](</Users/nick/Documents/New project/lib/reportportal_cucumber/automation/evidence_redactor.rb:117>), [http_exchange.rb:31](</Users/nick/Documents/New project/lib/reportportal_cucumber/automation/http_exchange.rb:31>).
- Scenario and impact: a recorded HTTP body contains a credential field whose key is JSON-escaped, for example the spelling `pass\u0077ord`, inside a prefixed diagnostic or truncated JSON document. Whole-string JSON parsing fails and the fallback regex cannot recognize the decoded key. The sensitive value survives rendering and is published by `AppLog.http`. This is within the HTTP helper's advertised credential-redaction boundary, not a demand to sanitize ordinary legacy `rp_log` or raw media.
- Evidence: independent malformed and embedded escaped-key probes both returned `marker_visible=true`; structured and ordinary form controls returned false. A fresh real Cucumber 10.2 subprocess published the synthetic marker to the RP request body. A separate post-process inspection confirmed it in the native Cucumber attachment too. Only synthetic markers were used. No deployed RP upload was performed. The stronger `EvidencePresenter` security regressions passed, but `HttpExchange` bypasses that fail-closed diagnostic policy.
- Mitigation/gate: validate ambiguous escaped JSON-shaped/embedded content before falling back to plain-text rendering, or omit it safely; apply the policy before clipping. Add native AppLog HTTP tests covering every sink, including malformed and embedded escaped keys. Preserve readable safe controls and original business exceptions.

### D3 [P1] Optional MinIO Upload Disables HTTPS Server Authentication

- Source: [minio_uploader.rb:22](</Users/nick/Documents/New project/lib/reportportal_cucumber/transport/minio_uploader.rb:22>).
- Scenario and impact: production selects `minio_markdown` and an HTTPS object-storage endpoint. The uploader unconditionally sets `ssl_verify_peer=false`, so HTTPS does not authenticate that server. An untrusted intermediary can receive confidential recordings or supply untrusted upload responses. No configuration restores verification on this client path.
- Evidence: a fresh constructed uploader's SDK configuration reported `verify_peer=false`. This is a verified configuration defect; no interception experiment or real credential use was attempted. The [official AWS Ruby SDK reference](https://docs.aws.amazon.com/sdk-for-ruby/v3/api/Aws/S3/Client.html) documents peer verification as enabled by default and supports CA configuration.
- Mitigation/gate: preserve SDK verification and allow a trusted CA bundle/store where necessary. Require invalid-certificate rejection and trusted-certificate success before enabling this optional path in production. Multipart reporting is not affected by this finding.

### D4 [P1] Helm Public-To-Private Transition Leaves Prior Anonymous Bucket Policy Intact

- Source: [minio-init-job.yaml:87](</Users/nick/Documents/New project/helm/reportportal-rich-experience/templates/minio-init-job.yaml:87>).
- Scenario and impact: an operator changes `videoBucket.makePublic` from its demo default true to false when adopting a production profile. The upgrade hook skips policy assignment entirely; it never removes the policy already stored in MinIO. The bucket can remain anonymously accessible, with the ingress route still enabled. A false value is therefore not evidence that existing recordings became private.
- Evidence: local Helm rendering with `makePublic=false` and an existing-secret reference produced only the true-branch policy command, with no private/none branch. Source examination confirms no revocation elsewhere in these templates. The focused follow-up executed the unchanged baseline hook shell using an offline `mc` function stub: true issued `anonymous set public`; false issued no policy command and exited successfully. The pinned [mc SetAccess implementation](https://github.com/minio/mc/blob/RELEASE.2025-07-21T05-28-08Z/cmd/client-s3.go#L1443-L1479) reads/modifies/writes policy only on an explicit call; bucket creation with `--ignore-existing` does not reconcile policy. The tagged [private/none mapping](https://github.com/minio/mc/blob/RELEASE.2025-07-21T05-28-08Z/cmd/anonymous-main.go#L217-L244) selects `none`, and an empty resulting policy causes [minio-go v7.0.90 to delete the bucket policy](https://github.com/minio/minio-go/blob/v7.0.90/api-bucket-policy.go). That revocation path is absent from this hook. This validates D4 without a live upgrade, policy mutation or anonymous request; it does not certify removal of arbitrary separately managed custom grants.
- Mitigation/gate: reconcile both desired states and verify actual bucket policy, especially on an existing installation. Default public exposure and bundled demo administrator/storage credentials must not be treated as a production profile. A private bucket also needs a deliberately tested access mechanism for playback; alternatively keep external video mode disabled and use the existing RP attachment route. No infrastructure redesign or policy change was performed in this audit.

### D10 [P1] Addendum: Public-Read Bucket Setup Grants Anonymous Write And Delete

- Sources: [minio-init-job.yaml:88](</Users/nick/Documents/New project/helm/reportportal-rich-experience/templates/minio-init-job.yaml:88>), [values.yaml:36](</Users/nick/Documents/New project/helm/reportportal-rich-experience/values.yaml:36>), [values.yaml:69](</Users/nick/Documents/New project/helm/reportportal-rich-experience/values.yaml:69>), [ingress-extension.yaml:48](</Users/nick/Documents/New project/helm/reportportal-rich-experience/templates/ingress-extension.yaml:48>).
- Tagged primary-source fact check: the chart pins `mc RELEASE.2025-07-21T05-28-08Z`. Its [permission conversion](https://github.com/minio/mc/blob/RELEASE.2025-07-21T05-28-08Z/cmd/anonymous-main.go#L217-L244) maps `public` to `readwrite`, whereas `download` maps to `readonly`. Its [go.mod](https://github.com/minio/mc/blob/RELEASE.2025-07-21T05-28-08Z/go.mod#L25-L26) pins minio-go v7.0.90. That version's [policy generator](https://github.com/minio/minio-go/blob/v7.0.90/pkg/policy/bucket-policy.go#L49-L64) grants anonymous object `GetObject`, `PutObject`, `DeleteObject`, `AbortMultipartUpload` and `ListMultipartUploadParts`; bucket grants include `GetBucketLocation`, `ListBucket` and `ListBucketMultipartUploads`. [Wildcard principal/resources](https://github.com/minio/minio-go/blob/v7.0.90/pkg/policy/bucket-policy.go#L147-L215) apply these grants to the target bucket and its objects.
- Scenario and scoped impact: the requested PUBLIC READ playback setup instead authorizes unauthenticated upload, replacement/deletion of recordings and storage abuse, wherever the MinIO API is reachable and these grants are effective. The hook targets the bucket root, so `objectPrefix=videos` does not constrain the policy. Exposure is limited to that video bucket, not other RP buckets or administrative policy operations. The supplied ingress is not a read-only method filter. This is an unsafe supported setup, distinct from the deliberate choice to allow public reads and from D4's failure to revoke an existing policy.
- Evidence/status: FAIL by exact tagged-source trace and offline hook-command reproduction. `minio_policy_hook_probe.rb` and `minio-policy-hook-results.ndjson` contain the true/false command receipts. Live policy contents, anonymous write acceptance and external reachability were NOT TESTED; no anonymous-write probe or live policy mutation occurred. No claim is made that the deployed bucket was exploited.
- Mitigation/gate: use least-privilege read-only policy for the approved bucket/prefix, or private access; reconcile false desired state as in D4. Verify effective policy before enabling external playback. Keep external video disabled pending those gates. The NO-GO verdict is unchanged; D10 applies to the optional Helm/video production profile, not ordinary RP multipart attachments.

### D5 [P2] Evidence Publication Can Bypass Capture-Close And Finalization Deadlines

- Sources: [context.rb:237](</Users/nick/Documents/New project/lib/reportportal_cucumber/runtime/context.rb:237>), [context.rb:308](</Users/nick/Documents/New project/lib/reportportal_cucumber/runtime/context.rb:308>), [formatter.rb:176](</Users/nick/Documents/New project/lib/reportportal_cucumber/cucumber/formatter.rb:176>).
- Scenario and impact: a helper thread publishes multiple artifacts while a full queue uses the supported `block` overflow policy. `publish_capture_target` holds the context mutex across every potentially blocking admission. Close/finalization first waits to acquire that same mutex without a deadline; only afterward does its timeout start. The unbounded artifact list can multiply admission waits, delaying serial tests or process exit beyond the advertised shared budget.
- Evidence: with a full one-record queue, 100 ms admission timeout and twelve publications, `close_capture_targets(timeout: 0.01)` took 1,256 ms on the first run and 1,287 ms on the retained rerun, then returned true. No network was involved. Existing deadline tests cover active capture leases and transport delay, not blocked admission inside publication's mutex.
- Mitigation/gate: avoid holding context synchronization across blocking queue admission, bound evidence-batch size, and include mutex acquisition/publication in one absolute deadline. Add a native helper-thread/full-queue/finalization regression. Default rejection mode is less exposed; this is not a claim that all queue waits are unbounded.

### D6 [P2] Attachment Filename De-Duplication Can Generate A New Collision

- Source: [payload_builder.rb:579](</Users/nick/Documents/New project/lib/reportportal_cucumber/service/payload_builder.rb:579>).
- Scenario and impact: one batch contains `evidence.txt`, another `evidence.txt`, and a real `evidence-1.txt`. Generated names become `evidence.txt`, `evidence-1.txt`, `evidence-1.txt`. JSON file references no longer identify a unique binary part. The server may reject or associate the wrong evidence, especially with repeated screenshot/helper filenames in a batch.
- Evidence: the independent payload-builder probe returned those exact names and `unique=false`. Alignment validation accepts this payload because ordered name lists are equal; it does not enforce uniqueness. Existing tests cover repeated identical names, not collisions with generated suffixes. Deployed RP handling of this ambiguous wire payload was NOT TESTED, so server corruption is a risk rather than an asserted live observation.
- Mitigation/gate: reserve all emitted names, search for an unused suffix, and enforce unique wire filenames. Test permutations, sanitized-name collisions and pre-suffixed names with distinct bytes and item owners.

### D7 [P2] Disabled Formatter Can Abort Business Execution When Endpoint Is Unset

- Sources: [formatter.rb:28](</Users/nick/Documents/New project/lib/reportportal_cucumber/cucumber/formatter.rb:28>), [http_client.rb:26](</Users/nick/Documents/New project/lib/reportportal_cucumber/transport/http_client.rb:26>), [config.rb:290](</Users/nick/Documents/New project/lib/reportportal_cucumber/config.rb:290>).
- Scenario and impact: a consumer retains its formatter configuration but turns reporting off, or runs locally without an RP endpoint. Although `Config#enabled?` is false, the formatter eagerly constructs the HTTP client and calls `URI(nil)`. This raises `ArgumentError` rather than becoming a no-op. It is distinct from normal AppLog/native Cucumber operation with the RP formatter omitted, which passed.
- Evidence: fresh formatter construction with no endpoint failed. A native CLI probe with `RP_ENABLED=false` and no endpoint exited 2 before the business action ran. Cucumber's `BeforeAll` had run and `AfterAll` did not run in this case. No reporting request was made.
- Mitigation/gate: defer transport/background resources until reporting is enabled, or construct an inert disabled runtime. Add native disabled/missing/partial-configuration tests asserting unchanged business execution and teardown behavior.

### D8 [P2] Native AfterAll Failure Occurs After RP Has Been Finalized As Passed

- Sources: [formatter.rb:694](</Users/nick/Documents/New project/lib/reportportal_cucumber/cucumber/formatter.rb:694>), [formatter.rb:719](</Users/nick/Documents/New project/lib/reportportal_cucumber/cucumber/formatter.rb:719>). Verified native dependency order: [Cucumber runtime.rb:81](/opt/homebrew/lib/ruby/gems/3.4.0/gems/cucumber-10.2.0/lib/cucumber/runtime.rb:81).
- Scenario and impact: all scenarios pass, then native run teardown (`AfterAll`) raises. Cucumber 10.2 emits `test_run_finished` before invoking `AfterAll`, so this formatter has already closed the launch and cannot account for the teardown failure. Testers see a passed RP run while the real process fails. Native run hooks also do not become the class-hook items exercised by synthetic formatter events.
- Evidence: the independent native probe observed `cucumber_exit=2`, `launch_status=passed`, `receipt_complete=true`, both run hooks executed, zero class-hook items and three method-hook items. The original teardown exception was preserved, which is PASS for business precedence but FAIL for report coverage. The normal control exited 0. The class-hook unit test injects fabricated `test_step_started` events; it is not evidence of native BeforeAll/AfterAll coverage.
- Mitigation/gate: explicitly account for run-hook failure before declaring whole-run reporting complete, or narrow/document this support boundary and make CI's actual process outcomes authoritative for shared launch completion. Add native run-hook success/failure tests; do not reinterpret the statistical Scenario STEP topology or add automatic browser lifecycle ownership.

### D9 [P2] MinIO Failure Diagnostics Bypass Credential Redaction

- Sources: [minio_uploader.rb:94](</Users/nick/Documents/New project/lib/reportportal_cucumber/transport/minio_uploader.rb:94>), [minio_uploader.rb:101](</Users/nick/Documents/New project/lib/reportportal_cucumber/transport/minio_uploader.rb:101>), [queue_processor.rb:655](</Users/nick/Documents/New project/lib/reportportal_cucumber/service/queue_processor.rb:655>).
- Scenario and impact: an upload error contains a sensitive URL or credential-like diagnostic value. Unlike the RP transport-warning and spool-metadata paths, this optional uploader writes the raw exception message to stderr and returns it as fallback text; the queue then publishes that text to RP. These diagnostic strings are not raw binary/video bytes and are within the stated transport-warning privacy concern.
- Evidence: a synthetic raising upload client made both `terminal_marker_visible` and `fallback_marker_visible` true. Source tracing confirms the latter becomes ordinary RP log text on degradation. The existing uploader failure test asserts the raw message is preserved but has no privacy control. No real upload error or secret was logged.
- Mitigation/gate: sanitize and bound warning/fallback text with the same diagnostic policy used elsewhere, while preserving degraded-evidence accounting and business failure precedence. Test stderr, RP wire text, URL fields and oversized errors. Keep this mode disabled until its security gates pass.

## Verdict And Minimum Gates

**NO-GO for the requested production design on this branch candidate.** The normal serial reporting path has substantial working implementation and fresh regression evidence, but the recommended shared-launch behavior is incompatible with CI-owned completion, and the HTTP helper leaks within its promised credential-redaction boundary. Test counts do not override these reproductions.

1. Establish the tested CI-owned shared-launch contract: explicit original UUID, no worker finish, unique run ownership, all-worker receipt/status collection, slow/failed/late worker cases and owner crash handling. Preserve the original business exit statuses.
2. Close D2's HTTP privacy gap and prove native Cucumber/RP sink safety. Keep the explicitly unsanitized legacy/raw-artifact paths under a consumer privacy policy; no universal PII-filter claim.
3. Resolve or explicitly restrict D5-D8 before rollout: bounded publication/close, unique attachment associations, inert disabled reporting and native run-teardown outcome handling. Confirm tester APIs retain original business exceptions.
4. If external video is enabled, close D3/D4/D9/D10 and verify certificate authentication, least-privilege read-only/private bucket policy, false-state revocation, sanitized failures and consumer-owned capture/retention. Otherwise keep this optional mode out of the production profile. Do not deploy demo credentials/default public ingress as production settings.
5. Complete M5 release certification for the exact artifact and required runtime/RP/browser combination. Use a new authorized version/release identity and reproducible baseline build; do not overwrite/relabel the historical `v1.1.0` artifact. Run realistic isolated-process workloads with dozens of serial UI cases and reconcile identities, logs, binary associations and receipts against the actual server/UI.

A restricted single-process or independent-per-worker pilot may be CONDITIONAL after privacy controls and operational receipt checks are established, with external video disabled. That is not approval for CI-owned shared-launch production use.

Tester-facing strengths reproduced include explicit `rp_evidence` ownership, path-backed RP attachments, readable status-aware HTTP summaries, native-only AppLog support, severity preservation, bounded previews and actionable spool refusal messages. The important usability failures are not cosmetic: optional reporting can prevent the test from running (D7), file suffixes can defeat evidence association (D6), and a failed run teardown can look fully passed in RP (D8).

Serial cases within one isolated worker fit the normal context model better than concurrent in-process scenarios.
