## Fix And Evidence

The output post-condition previously accepted any value starting with
`[REDACTED]`, so `[REDACTED]SYNTHETIC_SECRET` could pass. It also omitted standalone
Bearer values and normalized quoted JSON credential names from its inspection.

`EvidenceRedactor#encoded_credential_exposed?` now verifies complete mask values,
checks Bearer credentials, and reuses the existing quoted-key scanners and
sensitive-key normalization (including custom keys). The existing three-pass
percent-decoding budget and JSON Unicode handling are retained. Unsafe residual
values cause the existing safe-omission behavior; they are not silently accepted.
No per-message cache or shared mutable state was added. Non-percent-encoded input
still takes the existing early return.

The new specs cover encoded path segments, valueless query parts, fragments,
malformed URLs, normalized and Unicode-escaped names, complete versus prefixed
masks, safe URL preservation, and callers in HTTP evidence and failure cards.
Sentinel bytes themselves are encoded, and assertions inspect decoded output.
A separate logger spec proves that a caller-written curl, including its header,
body and encoded URL, reaches both ordinary reporting sinks byte-for-byte.

## Performance Method

This is an offline diagnostic of client-side processing, not HTTP delivery,
RP persistence, browser rendering, maximum throughput or a memory-leak soak test.
Terminal, Cucumber and RP sinks are no-ops for the ordinary logger measurement.

Three byte-verified runtime arms were measured: historical baseline `3f20313`,
third-party candidate `f49dab28`, and the patched candidate. The environment was
Ruby 3.4.12 / Cucumber 12.0.1, a pinned image and read-only dependency volume,
`--network none --cpus 1 --memory 2g`.

The frozen 21-case failure corpus was hash-verified and not edited. Each case had
10 warmups and 50 samples: **1,050 observations per mode, arm, round and boundary**.
Both renderer-only and complete formatter redaction-plus-rendering were measured.
Two rounds reversed runtime ordering, in fresh processes, for both plain and rich.
Separate supplementary inputs cover encoded URLs and 71-byte / 36,610-byte JSON
HTTP bodies. These do not replace or expand the frozen acceptance corpus.

### Harness Correction

The initial diagnostic copied a defect in the existing QA benchmark:
`Config.new("rp.presentation" => mode)` does not normalize dotted YAML keys and
therefore silently uses plain mode. Those initial records are retained under
`performance/`, but are **not** used for the mode-labelled results below.

The independent harness now uses `Config.new(presentation: mode)` and asserts both
the resolved config and the renderer keyword. All arms and rounds were rerun in
`performance-mode-verified/`. The historical QA script was left unchanged; its
mode selection must be corrected before a future formal plain/rich G11 run.

Values are p95 milliseconds; pairs are rounds 1 / 2, not selected best runs.

| --- | --- | --- | --- |
| Redaction + rendering, plain | 6.326 / 6.007 | 4.101 / 4.034 | **3.982 / 3.948** |
| Redaction + rendering, rich | 6.692 / 6.751 | 4.118 / 4.157 | **4.184 / 4.011** |
| Rendering only, plain | 1.249 / 1.153 | 1.270 / 1.254 | **1.063 / 1.056** |
| Rendering only, rich | 1.766 / 1.876 | 1.285 / 1.175 | **1.066 / 1.064** |

The full-path p95 is 34.3-40.6% below the historical baseline in these runs.
Relative to the immediately preceding candidate, it varies from -3.5% to +1.6%:
no material regression was observed in this diagnostic. This does not prove the
new security check made normal input faster. The frozen corpus has no percent
escapes, and the unchanged fast path applies.

The patched and pre-patch full paths allocate the same measured average of
1,748.44 objects per failure on that corpus. The historical baseline allocates
2,021.60 in plain and 3,349.86 in rich. The rich difference includes earlier removal
of rich-only failure-card rendering; it is not attributable to this security patch.
Allocation counts are not peak RSS or a proof of absence of memory leaks.

### Current Local Processing Costs

Ranges cover both measured rounds and modes, in milliseconds at p95.

| Operation | Patched p95 | Scope |
| --- | --- | --- |
| Ordinary reproduction-curl logger | 0.011-0.026 | Dispatch to no-op sinks; no terminal/network latency |
| Small JSON HTTP evidence | 1.40-1.97 | Exchange construction, automatic redaction and Markdown |
| 36,610-byte JSON HTTP evidence | 23.27-27.12 | Same boundary, 64 trade records |
| Double-encoded Bearer URL | 0.052-0.079 | Direct URL redaction |
| Double-encoded mask-prefixed credential URL | 0.179-0.255 | Direct URL redaction |
| Failure redaction + rendering | 3.95-4.19 | Frozen 21-case formatter corpus |

The encoded post-condition is not free: the safe encoded-URL probe allocates
124.02 objects/call versus 117.02 before, and the Bearer probe 165.02 versus 152.02.
The normal unencoded URL stays at 70.02. Those small absolute costs should not be
confused with the much larger cost of repeatedly formatting complete JSON bodies
(about 53,000 objects/call for the large fixture).

Practical assessment: ordinary reproduction logs remain inexpensive; frequent
large HTTP bodies are the more important cost to budget. Prefer concise summaries
for frequent events and retain full bodies as explicit evidence when needed.
Do not infer online logs/second from these no-network measurements.

## Remaining Limits

- **G11 is not certified.** Host loadavg was about 20 on eight CPUs and the RP
  container remained active. The original quiet-window conditions were not met.
  The historical +67.4% failure and NOT RUN records remain intact.
- The fix is tested within the existing percent/Unicode decoding policy. Arbitrary
  encoding depth, base64 and HTML entities are not newly supported.
- CI, live RP/UI checks P1.6 / P10.8 / P10.10 / P10.11, and the separate named F18
  acceptance work were not executed in this follow-up. No RP data was modified.
- The ordinary raw logging path intentionally remains raw. This fix does not
  classify every caller-supplied log or attachment as automatically sanitized.
- No production-ready verdict, release approval or long-duration memory-stability
  claim follows from these local results.
